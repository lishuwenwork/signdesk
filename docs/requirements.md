# 签行 SignDesk · 需求文档

版本：v1.1 Web 设计评审稿

日期：2026-10-08（北京时间）

产品形态：个人使用、单实例运行的 Web 系统

正式版技术方向：Java 21 + Spring Boot 4.x / Spring MVC + Vue3 / JavaScript + SQLite / MyBatis-Plus + Hutool

设计阶段交付（历史）：需求、架构、使用说明、单文件 HTML 交互原型及设计包。
当前实现：仓库包含实际 Spring Boot 后端、Vue 页面和可构建的单 JAR；已实现范围与验证结果见 README.md 和 validation.md。原型站点仍为独立的交互评审用途。

## 1. 产品目标与已确认决策

用户经常复制 cURL 进行签到，希望把多个平台、多个账号的完整请求集中保存，按平台设置时间并执行，减少手工操作。

| 已确认项 | 产品决定 |
|---|---|
| 请求输入 | 默认粘贴完整 cURL，不要求手动提取 Cookie、Token 或套用公共模板 |
| 鉴权差异 | 保留 URL、Method、Headers、Query、Body 以及支持的请求选项；鉴权字段可以位于任意位置 |
| 账号关系 | 平台下有多个账号，每个账号可以有多个独立请求 |
| 定时归属 | 平台独立配置计划；A 每天 09:00，B 每天 10:00 |
| 执行范围 | 平台、账号、请求各有启用状态；只有同时启用的请求参与平台定时 |
| 后端技术 | Java 21、Spring Boot、Spring MVC；HTTP 请求直接使用 Hutool HttpRequest |
| 前端技术 | Vue3、JavaScript、Element Plus；工程构建使用 Vite |
| 数据保存 | SQLite 文件数据库，通过 Xerial JDBC 和 MyBatis-Plus 访问 |
| 调度技术 | Spring TaskScheduler 与 SQLite 持久任务表；不使用 Redis |
| 认证范围 | 第一版不实现应用内登录、Session、JWT 或权限体系 |
| 工程组织 | 同一仓库包含 frontend 和 backend 两个工程；前端构建结果打入后端 JAR |
| 部署形式 | 一个 Spring Boot 服务和应用外部的 SQLite 数据目录 |
| 初期目标 | 先评审交互原型，再开发真实 Web 系统 |

## 2. 第一版范围

### 2.1 必须包含

1. 平台新增、修改、停用、删除。
2. 账号新增、改名、停用、删除。
3. 粘贴完整 cURL、解析预览、保存请求、整份更新请求。
4. 每个请求的结果判断规则和启用状态。
5. 单请求、平台、全部平台的手动执行。
6. 平台的每日／指定星期计划、多个时间点、时区、请求间隔。
7. 全局暂停定时、平台独立暂停、执行队列和运行中状态。
8. 成功、已完成、失败、凭证过期、结果待确认、已取消等执行结果。
9. 执行记录、筛选、详情、原始请求版本关联。
10. 正式版的服务器持久保存、完整请求加密、服务重启恢复、配置备份与恢复。
11. 浏览器关闭后继续执行；其他设备访问同一服务时查看统一配置和记录。

### 2.2 后续扩展

- 多步工作流、响应变量提取、Token 自动刷新。
- 经用户配置的平台签名算法和动态参数生成。
- 相同结构的请求模板及账号变量。
- 自定义 Cron、更多 IANA 时区和夏令时测试。
- 平台适配插件、多用户数据隔离和应用内登录认证。
- 文件上传、客户端证书、高级代理等 cURL 扩展。

第一版不自动推断登录流程、破解签名或自动处理验证码。完整 cURL 是一次请求快照；短期凭证、一次性参数仍会失效。

## 3. 用户操作流程

### 3.1 首次接入

1. 打开 Web 管理页面，新增平台，例如「平台 A」。
2. 在平台下添加账号，例如「主账号」。
3. 粘贴该账号的完整 cURL。
4. 查看解析后的 Method、URL、请求头、Query 和 Body；确认未丢字段。
5. 为请求命名，设置成功／已完成／凭证过期等规则。
6. 手动执行，核对平台实际结果。
7. 设置平台计划，例如每天 09:00，启用定时。

关闭网页后，正式版由服务器继续调度。用户电脑只负责访问页面，执行请求使用部署服务器的网络出口。

### 3.2 新增另一个账号

重复添加账号和粘贴 cURL 的操作。不同账号可以有不同 URL、鉴权字段和请求体；不会自动共用 Cookie 或修改字段。

### 3.3 请求失效后更新

点击「更新 cURL」，粘贴新请求，生成新的请求版本。保留平台、账号、请求 ID、计划、结果规则与历史记录。已成功的当日记录不自动清除；需要再次发送时使用明确的「重新执行」。

### 3.4 排查执行结果

在概览或日志中定位失败请求，查看触发来源、请求版本、HTTP 状态、业务判断、耗时、错误摘要。凭证失效时更新 cURL；结果待确认时先查询平台状态，避免直接重试造成重复操作。

## 4. 数据对象

| 对象 | 主要字段 | 规则 |
|---|---|---|
| 平台 Platform | ID、名称、备注、启用状态、默认间隔、时区 | 平台是分组和定时边界 |
| 账号 Account | ID、平台 ID、别名、备注、启用状态 | 别名用于用户识别，不承担鉴权字段提取 |
| 请求 Request | ID、账号 ID、名称、启用状态、当前版本、结果规则 | 一个账号支持多个请求 |
| 请求版本 RequestRevision | 版本号、原始 cURL、解析结果、创建时间 | 保存完整快照，含敏感内容时整体加密 |
| 平台计划 Schedule | 平台 ID、启用、每日／每周、星期、时间点、时区、补执行策略 | 一个计划支持多个时间点 |
| 触发批次 Occurrence | 平台 ID、计划版本、计划时刻、来源、批次状态 | 同一计划触发点只创建一次自动批次 |
| 执行记录 Run | 请求 ID、请求版本、批次 ID、业务日期、来源、状态、HTTP 状态、耗时、摘要 | 每次尝试独立保留 |
| 当日完成 DailyCompletion | 请求 ID、平台业务日期、完成记录 ID | 与日志分开保存，避免清理日志后重复签到 |
| 全局设置 Settings | 暂停定时、并发上限、超时、日志保留 | 不替代平台计划 |

## 5. 功能需求

### FR-01 平台管理

- 平台名称必填，最长 40 个字符；默认名称可为「平台 A」。
- 平台停用后不接收新的执行任务；需要手动执行时先重新启用。
- 删除平台前提示将同时删除其账号、请求、计划与关联记录。
- 正在执行的请求不可被直接删除；先取消队列，等待当前请求结束或中止。

### FR-02 账号与请求管理

- 账号别名必填，平台内允许用户自行区分重名，但界面提供提醒。
- 账号停用不改变其他账号的请求和计划。
- 请求独立命名、启停、编辑规则、更新 cURL。
- 请求名称默认「每日签到」。新请求默认使用平台计划。
- 一个账号多个请求时按顺序执行，先后步骤之间暂不自动传变量。

### FR-03 cURL 导入与更新

| 内容 | 第一版要求 |
|---|---|
| 格式 | 支持浏览器常见 Copy as cURL（Bash、Windows CMD）；PowerShell 格式在无法可靠转换时提示用户重新复制 |
| 协议 | 仅 HTTP / HTTPS |
| URL | 保留查询参数、重复参数和原有编码；不随意重写带签名的 URL |
| 方法 | 处理 `-X` 及 `-d`、`-G` 等产生的默认方法和语义 |
| 请求头 | 处理 `-H`，保留重复项；自动生成的传输头不能改变请求语义 |
| Cookie | 处理 `-b` 的内联 Cookie，与原请求头按明确规则保持一致 |
| Body | 处理 `--data-raw`、内联 `--data-binary`、`--data-urlencode` 和多个 `-d` 的组合语义 |
| 常用选项 | 重定向、超时、压缩等逐项映射；无法映射的选项明确提示，不静默忽略 |
| 暂不支持 | `@文件`、文件上传、管道、多条命令、外部命令替换、配置文件引用等 |

- 原始 cURL 与结构化请求同时保留，禁止把原始内容直接交给 shell 执行。
- Hutool 负责 HTTP 发送；cURL 的分词、选项语义和导入诊断由项目中的解析器实现。
- 不会主动删除看似多余的请求头、时间戳、签名或设备标识。
- 使用 HTTP 客户端执行导入请求不能保证所有浏览器指纹或高级 cURL 行为完全等价；必须经过试运行。
- 多账号执行时禁止共享自动 Cookie 会话；每次使用独立请求对象和该账号快照中的鉴权信息。
- 服务端网络出口可能与复制请求的电脑不同；IP 绑定、一次性签名、验证码等需按平台实际行为验证。
- 导入失败给出具体位置或不支持的选项，保留用户输入供修正。
- 导入新版本时显示可检查的变更摘要；请求体始终保留原始字节表达或明确的编码方式。

### FR-04 结果判断

用户按平台实际返回配置规则，HTTP 200 不自动等于签到成功。

| 分类 | 判断与处理 |
|---|---|
| 成功 success | 匹配用户配置的成功规则，计入完成 |
| 已完成 already_done | 匹配平台「已签到」业务码，计入完成 |
| 凭证过期 expired | HTTP 401 或已配置的未登录业务码；提示更新完整 cURL，暂停自动执行该请求直到更新 |
| 失败 failed | 明确匹配业务失败规则或确定未成功的请求错误 |
| 待确认 unknown | 已发送但超时／断开，或响应无法判断；不自动判为失败重试 |
| 取消 cancelled | 尚未发送的排队项可直接取消；已发送项依据中止时机保留待确认结果 |

结果规则第一版采用 JSON 字段路径、等于值和可选文本包含，支持规则试算。JSON 值保留类型，例如数字 `0` 与字符串 `"0"` 不默认等同。不执行用户输入的 JavaScript。消息字段由用户指定。

### FR-05 手动与批量执行

- 提供单请求、整个平台和全部已启用平台的执行入口。
- 批次只包含当时启用的账号与请求；创建时冻结请求版本和规则快照。
- 同平台默认串行，账号内请求也按顺序执行；间隔默认 2 秒。
- 不同平台限制同时执行的平台数，默认 2。
- 同一请求已有活动执行时，不会重复启动，提示「正在执行」。
- 手动执行接口先持久创建批次和排队项，再返回批次 ID；用户关闭页面或页面请求断开不取消后台任务。
- 可取消剩余队列。默认不开启不确定请求的自动重试。
- 全局暂停定时只影响新的自动触发，不中断已执行请求，手动入口继续可用。

### FR-06 平台定时

- 每个平台独立设置每日或指定星期、一个或多个时刻，时间精度到分钟。
- 默认时区为 `Asia/Shanghai`；第一版可选择北京时间或 UTC。
- 平台 A 每天 09:00，平台 B 每天 10:00，应独立生效。
- 配置 09:00 的含义是该平台批次在 09:00 开始，而非所有账号同时发送。
- 平台计划默认开启「每日成功后跳过」，适合签到。关闭后每个计划时刻都可执行，适合查询等重复任务。
- 同一自动触发点采用去重记录；手动「重新执行」允许有意识地覆盖每日跳过策略。
- 已启用请求被暂停／过期时不加入自动批次，界面显示原因。
- 当前业务周期存在待确认结果时暂不自动重发；用户核对平台状态后可以主动重新执行。
- 修改时间或星期后，下次执行时间立即更新；新计划只影响生效时间之后的触发点，已开始的批次保持快照。
- 服务器每 5 秒扫描一次有效计划，事务性领取触发点并创建持久队列；实际启动还受负载、间隔和并发上限影响，不承诺实时或毫秒级调度。
- 同一平台、同一 UTC 计划时刻只创建一个自动批次；计划版本作为快照属性保存，编辑计划不会把已领取的相同时刻重新执行。

### FR-07 页面关闭、服务重启与补执行

- 正式版调度在 Spring Boot 服务中运行，与网页是否打开无关。
- 关闭网页、退出浏览器或关闭用户电脑不影响服务器任务；停止服务、服务器关机或休眠期间无法执行。
- 每个平台可选择「不补执行」或「在允许窗口内补执行」，例如计划后 2 小时内。
- 服务启动后恢复计划和持久队列，只检查当前业务日期的有效触发点；不补历史几天的签到。
- 发送前持久记录执行中状态。服务崩溃后，无法确认结果的执行标记待确认，不直接重放；尚未发送的排队项先检查完成状态和有效窗口。
- 补执行前检查批次去重、每日完成状态、账号启用状态和凭证暂停状态。
- 多个错过时刻在每日跳过模式下合并为一次必要执行；重复任务模式逐项按有效窗口处理并设置上限。
- 服务器时钟变化后重新计算计划。业务日期根据平台所选时区计算，与访问设备时区无关。

### FR-08 日志与隐私

- 展示触发来源、平台／账号／请求、请求版本、时间、HTTP 状态、业务结果、耗时和安全摘要。
- 支持平台、状态、来源筛选与分页。默认保留 30 天，正式版可配置。
- 原始请求、URL 查询参数、Headers、Body、响应内容都可能含敏感信息。
- 默认日志不保存原始请求参数和完整响应，只保存必要元数据与允许字段。
- 原始请求详情来自服务器加密请求版本，按需查看；界面默认遮罩敏感值。
- HTML 原型不发送真实请求，不将用户粘贴的完整 cURL 写入浏览器持久存储或配置导出。

### FR-09 设置和备份

- 超时默认 20 秒，全局平台并发默认 2；默认关闭自动重试。
- 可配置日志保留天数；服务启动方式由部署配置管理。
- 普通配置导出默认排除请求内容。包含完整请求的正式版备份需密码加密，采用可迁移格式；服务器运行密钥与数据库文件分开管理。
- SQLite 存于 JAR 外部的数据目录，更新程序不覆盖已有数据库。运行中备份采用一致性快照；恢复时停止服务并校验备份和密钥。
- 导入前校验版本和数据结构，预览将新增或替换的内容；失败时不破坏现有配置。

### FR-10 Web 访问与部署

- 前后端在一个仓库内分别开发，正式发布合成一个 JAR；运行环境只需 Java 和可写的数据目录。
- 前端通过同源 `/api` 接口操作后端。开发环境由 Vite 代理接口；正式环境由 Spring Boot 提供静态页面和接口。
- 第一版不提供登录页、账号注册、Session、JWT 或角色权限，不依赖 Spring Security、Redis 或独立数据库服务。
- 默认按个人工具部署，后端监听本机地址；需要远程使用时通过确定的私有访问入口访问。现有 HTML 预览仍保持所有者私有权限。
- SQLite 数据文件、加密密钥、日志目录与程序包分开保存；服务启动时校验目录和密钥、执行数据库迁移并取得实例锁。
- 只允许一个实例使用同一数据目录执行任务。初版不提供多节点调度。

## 6. 页面与交互设计

| 页面 | 主要内容 | 主要操作 |
|---|---|---|
| 今日概览 | 今日参与任务、已完成、需处理、下次执行、最近记录 | 执行全部、进入平台、查看异常 |
| 平台与账号 | 平台选择、账号列表、账号下完整请求 | 新增平台／账号／请求、启停、更新 cURL、单次执行 |
| 定时计划 | 各平台的时间、星期、时区、范围、下次执行 | 编辑计划、独立开关、模拟触发点 |
| 执行记录 | 记录筛选、状态、版本、耗时、响应摘要 | 查看详情、定位请求、重新执行 |
| 设置 | 超时、并发、日志、备份、后台运行说明 | 保存配置、导出、导入、恢复演示数据 |

新增账号采用「粘贴 cURL → 解析预览 → 结果规则」三步表单。使用者不必手工区分 Token、Cookie、签名或设备参数。

## 7. 非功能要求

| 项目 | 目标与验证方式 |
|---|---|
| 易用性 | 添加账号只需别名和完整 cURL；其他规则可复用平台默认值，但请求内容保持独立 |
| 部署 | 一个 Spring Boot 服务；SQLite 在部署机器本地磁盘，前端与接口同源 |
| 后台运行 | 浏览器关闭不影响正式任务；服务停机后的恢复遵循补执行和待确认规则 |
| 响应性 | 请求与异步等待不阻塞界面；批量导入或迁移在后台处理 |
| 稳定性 | 单账号错误不阻断其他账号；重启能恢复计划并标记中断执行 |
| 保密性 | 包含凭证的整个请求版本加密，不仅加密名为 Cookie／Token 的字段 |
| 资源 | 正式版测量 JVM 进程总内存、堆与本地内存、线程数、CPU 和 SQLite 大小；不沿用桌面原型的内存估算 |
| 长期运行 | 检查多轮执行与至少 24 小时运行后的内存趋势、队列残留和日志增长 |
| 数据稳定性 | 短事务、单写入协调、忙等待超时和版本迁移；HTTP 网络等待不持有数据库事务 |
| 兼容性 | 以 Java 21、Windows / Linux 服务运行和现代桌面／移动浏览器为验证对象 |
| 可访问性 | 键盘可操作、表单有标签、状态有文字、窄屏原型可使用 |

## 8. 验收用例

| 编号 | 用例 | 通过标准 |
|---|---|---|
| AC-01 | 导入带 Cookie、Authorization、设备头、Query、JSON Body 的 cURL | 所有业务字段在解析预览与执行快照中保留 |
| AC-02 | 同平台两个账号使用不同请求结构 | 执行时互不串字段、Cookie 和响应变量 |
| AC-03 | 平台 A 09:00，B 10:00，服务持续运行 | 分别在对应时刻触发；已领取的 A 批次不在 10:00 重复生成 |
| AC-04 | 停用一个账号／请求 | 自动批次不包含该项 |
| AC-05 | 一个账号添加两个请求 | 独立保存、显示和按配置顺序执行 |
| AC-06 | 替换 cURL | 请求 ID、规则、计划和历史保留，版本递增 |
| AC-07 | HTTP 200 返回失败业务码 | 不标记为成功 |
| AC-08 | 请求已发出后超时 | 标记待确认，不盲目自动重试 |
| AC-09 | 重复调度、手动与自动同时到达 | 同请求不并行，同触发点不重复建批次 |
| AC-10 | 每日已完成后再次定时 | 默认跳过；关闭每日跳过后可在下一时刻执行 |
| AC-11 | 服务器停机后在允许窗口内恢复 | 只补有效当前周期，遵守完成和暂停状态 |
| AC-12 | 凭证失效后更新 cURL | 解除该请求的凭证暂停，保留原计划 |
| AC-13 | 编辑运行中的请求 | 阻止当前编辑或保持冻结快照，记录实际版本 |
| AC-14 | 服务退出后重新启动 | 加密请求可恢复，未确认的执行被标记待确认 |
| AC-15 | 导出配置或查看日志 | 不泄露任意位置的凭证、原始请求或响应敏感字段 |
| AC-16 | HTML 原型执行 | 只产生模拟结果，不发生对外请求 |
| AC-17 | 创建批次后关闭网页，再由另一设备打开 | 正式任务继续运行，可查看同一批次的状态与记录 |
| AC-18 | 更新 JAR 后重新启动 | 原有 SQLite 数据和密钥保留，版本迁移不覆盖配置 |
| AC-19 | 没有 Redis、MySQL 和登录配置 | 正式应用可启动并完成基础功能 |
| AC-20 | Hutool 执行签名 URL、重复字段及两个账号请求 | 对照实际发送字节验证支持范围，账号凭证不互相串用 |

## 9. 原型边界

原型是可直接打开的单文件 HTML，使用原生 JavaScript 和 CSS，方便评审；正式前端按 Vue3 + JavaScript 实现，正式业务执行由 Spring Boot + Hutool 实现。

原型包含真实的界面状态变化、增删改、常见 cURL 解析、模拟队列、平台计划编辑、定时预演、筛选、记录详情和无凭证配置导入导出。新增配置在当前浏览器保存，但用户粘贴的完整请求只在本次页面内存保留，刷新后需要重新粘贴。

原型不连接平台、不实现 Spring Boot 服务、SQLite 持久队列、服务器加密、可靠后台定时或真实资源测量。模拟执行的成功与失败来自演示场景，不能用于验证平台接口是否有效；关闭原型页面会结束模拟任务。

现有私有链接只承载 HTML 原型。正式 Spring Boot 服务部署在具备 Java 运行环境的机器上；文档中的后端目录、REST 接口和数据库表均为实施设计。

## 10. 开发顺序

1. 评审本次原型：平台／账号关系、导入流程、计划设置、日志是否顺手。
2. 建立同仓库的 frontend / backend 工程，完成 Vue 页面与 Spring MVC 接口联调。
3. 接入 Xerial SQLite JDBC 和 MyBatis-Plus，完成数据库迁移、完整请求加密、Java cURL 解析和 Hutool 单请求发送。
4. 完成持久队列、业务判断、请求版本、日志和单请求互斥。
5. 完成平台调度、触发去重、服务恢复和补执行。
6. 以两个真实平台、每个平台至少两个账号验证，构建包含前端资源的 JAR，并验证数据目录保留和备份恢复。
